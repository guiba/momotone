# AGENTS.md - AI Assistant Context for gesture_rust

This document provides structural and architectural context to guide AI assistants in working with this codebase.

## Project Overview
`gesture_rust` is a real-time hand gesture recognition engine in Rust: OpenCV captures webcam frames, an **ONNX two-stage hand pipeline** (BlazeHand detector → landmark detector, via `ort`) produces a hand box plus 21 landmarks, a **strategy** turns those landmarks into a `GestureEvent`, and the **event bus** dispatches it to sinks (audio, MIDI) while an **iced dashboard** renders the live HUD.

> **Current status (Nov 2026):** the vision pipeline works end-to-end and the local gate `make verify` (check + test + fmt + `clippy --all-targets -D warnings`) is green; the only warning left is a third-party `block v0.1.6` future-incompat notice. The frame loop lives in `src/pipeline.rs` and runs on **its own thread**; `main.rs` hands the main thread to the **iced** dashboard (`src/dashboard/`), so rendering never blocks inference. `tokio` is used only as iced's async executor (`features = ["rt", "time"]`). The detector stage is solid; the landmarker stage runs and returns 21 landmarks but is only lightly validated. The scaffolding from earlier iterations (`sources/mock.rs`, the unused strategies, the `Source`/`Tracker` traits, `Visualizer::draw_hud`, `GestureEvent.event_type`) has been deleted.

## Tech Stack
- **Language**: Rust (Edition 2021)
- **Vision / inference**: `opencv` 0.100 (`clang-runtime` feature), `ort` 2.0.0-rc.13 (ONNX Runtime) — the model tensors are plain `Vec<f32>` buffers handed to ort as `TensorRef` views, so there is no array crate in the dependency list
- **Audio**: `cpal` 0.17 (`Synthesizer` with a `Voice` sine oscillator)
- **MIDI**: `midir` 0.11 (`MidiOutputEngine`)
- **Messaging**: `crossbeam-channel` (unbounded MPMC) — the event bus
- **UI**: `iced` 0.14 (`canvas`, `image`, `tokio` features) — native dashboard window; `wgpu` renderer
- **CLI**: `clap` 4.5 (derive); `serde`/`serde_json` on the event types
- **Async**: `tokio` 1.36 (iced's executor); concurrency is `std` threads + `Mutex`/`Arc`/`AtomicBool`
- **Error handling**: `anyhow`

## Build Environment
- `.cargo/config.toml` forces `LIBCLANG_PATH` / `DYLD_LIBRARY_PATH` to `/opt/homebrew/opt/llvm/lib` (Homebrew LLVM) so the `opencv` build script finds clang. Do not remove it on macOS.
- OpenCV is built by the crate's build script on first compile; `target/` is ~1.7 GB and is gitignored.
- Quick verification loop: `cargo check` (≈4 s warm) rather than a full build.
- The gate before any commit is `make verify` (`check` + `test` + `fmt --check` + `clippy --all-targets -D warnings`). There is no CI: everything runs locally through the `Makefile` (`make help` lists the targets).

## Core Architecture & Data Flow
One frame per iteration of `Pipeline::run`, on a dedicated thread:

```text
next_frame()  ->  advance()  ->  HandEstimator.update()  ->  Strategy.process()  ->  EventBus.dispatch()
(camera/mock)     (stages)       raw detection -> HandState   HandState -> Performance  -> Sink.handle()
                      |
                      +-- hand_over() -> Presenter (own thread): RGBA preview, ASCII art, dump/stdout
                      |
                      +-- publish() -> FrameMetrics (Arc<Mutex>) -> Dashboard (iced, main thread)
```

1.  **Input Phase**:
     *   `src/vision/camera.rs`: `WebcamSource::get_frame()` returns an OpenCV `Mat` (BGR), flipped horizontally by default so the stage behaves like a mirror (the user's right hand appears on the right, matching the keyboard's low-left/high-right layout), using a scratch `Mat` the source keeps so the flip allocates once, not per frame; `new(camera_id, width, height, fps, mirror)` requests a capture resolution (default 640×480) and frame rate (default 30; best effort, `reported_fps()` returns what the driver actually gives). `--no-mirror` keeps the raw camera orientation.
    *   Mock mode is generated by `synthetic_detection()` in `src/pipeline.rs`, which builds an animated 21-landmark hand (no webcam, no ONNX assets) paced at ~30 fps by a deadline clock. There is no separate source abstraction: `next_frame` returns either a camera frame or a synthetic one, and everything downstream (`advance`) is identical for both. A `--video` source would slot into `next_frame`.

2.  **Vision Phase** (`src/vision/tracker.rs`):
     *   `HandTracker` is an enum, `MediaPipe(Box<MediaPipeTracker>)` or `YoloPose(Box<YoloPoseTracker>)`, chosen by `--model` in `main.rs::build_tracker`. Both arms return the *same* `HandDetectionResult` (21 MediaPipe-ordered landmarks + a square hand box in frame pixels), so strategies, the dashboard and the visualizer are model-agnostic. `process_frame` dispatches and then applies the shared landmark cache.
     *   `MediaPipeTracker` (formerly `HandTrackerImpl`) —
     *   Stage 1 — `run_detector()`: a **square window that follows the hand** (`detector_crop(palm, fw, fh)`) resampled to **192×192** via `sample_affine_to_tensor(frame, Affine, w, h, &mut StageInput)` (`src/vision/sampling.rs`; OpenCV `resize` on the crop — `warpAffine` if it runs off the frame edge — then one bulk BGR→RGB `/255` pass). The side is `min(W,H)`; its origin is slid so it contains the palm centre seen last frame, clamped to the frame. With no history this is the centred square — at 640×480 that sampled only x = 80..560, which is why the outer keyboard keys were physically unreachable. The anchor is EMA-smoothed (`ROI_ANCHOR_WEIGHT = 0.3`) and dropped after `ROI_STALE_FRAMES = 10` consecutive misses (`note_miss`), so a hand that leaves the view does not pin the window. Each stage has a reusable `StageInput { warped: Mat, data: Vec<f32> }` allocated once in `MediaPipeTracker::new`, and ort is handed a zero-copy `TensorRef` view over `data`; the sampler returns the mapping it actually applied so the box/landmark conversion uses the snapped crop. Outputs 2016 boxes (18 values per anchor) + 2016 raw scores; scores are **sigmoid**-ed, argmax wins, gated by `MediaPipeTracker::score_threshold` (`DEFAULT_SCORE_THRESHOLD = 0.6`, overridable with `--score-threshold`).
     *   Anchor offsets are converted to frame pixels and the palm box is **expanded ×2** to cover the whole hand. `run_detector` returns `PalmBox { cx, cy, half, score }`, and `r#box` is that square `(cx-half, cy-half, 2*half, 2*half)` reported **unclamped** - a constant size keeps the strategy's spread normalisation stable when the hand is clipped at the frame edge, and the canvas/OpenCV clip it when drawing.
     *   Stage 2 — `run_landmarks(frame, cx, cy, half)`: crops a square of side `half × 2 × 1.2` centred on the true palm centre (a hand clipped by the frame edge keeps its fingers in the crop; `warpAffine` pads the off-frame half with black rather than sliding the crop off the hand) into **224×224** and runs the landmark model; the 63 floats are mapped back to **frame pixel coordinates** (`Landmark { x, y, z }`). `--debug` prints the detector window origin, the winning anchor, the landmark bbox and all 21 landmark coordinates.
     *   **Landmark reuse** (`ReuseCache`, moved out of the tracker into `src/vision/reuse.rs` and shared by both backends): if the palm centre moves less than `LANDMARKER_REUSE_MOVE_PX` (3 px) and its half-size by under 3 %, the previous keypoints are reused and the 224×224 model is skipped for that frame — at most `LANDMARKER_REUSE_MAX_FRAMES` (3) frames in a row, and the cache is cleared whenever no hand is found. `--landmarker-always` disables the fast path for A/B testing.
     *   `src/vision/yolo_pose.rs`: `YoloPoseTracker` — a **single-pass** Ultralytics pose model (YOLOv8/v11/YOLO26 hand-pose exports). `run()` letterboxes the frame to the model's square input via `letterbox_map` + `sample_affine_to_tensor(..., TensorLayout::Nchw, LETTERBOX_PAD)` (the padding is black, matching Ultralytics' own `letterbox`), runs one inference, and `decode_pose` picks the highest-scoring detection. `decode_pose` is layout-agnostic: it accepts both the attribute-major `(1, 69, 300)` head of YOLOv8/v11 and the detection-major, NMS-free `(1, 300, 69)` head of YOLO26, reads the leading `[x1,y1,x2,y2,conf(,class)]` values and the trailing 21 × (x, y, visibility) keypoints, and maps everything back to frame pixels through the inverse of the letterbox affine. The graph's own declared input size wins over `--pose-input` (static exports reject other buffer sizes, and the tracker prints why). Keypoint order is MediaPipe's, so nothing downstream changes. `timings.detector_us` is the whole inference; `landmarker_us` stays 0.
     *   Measured on an M-series CPU (debug build, 640×640, one frame): YOLO26 pose ≈ 70 ms/frame vs. the MediaPipe two-stage ≈ 20 ms. The pose model is ~41 MB FP32 (21 MB FP16) vs ~15 MB for the MediaPipe pair, and its confidences run low (≈0.48 on a clear palm photo), so `--score-threshold 0.3` is a sane starting point for `--model yolo`.
    *   The tracker computes geometry only — it draws nothing. All overlays live in `src/visualizer/mod.rs`.
    *   Results are `HandDetectionResult { hand_landmarks: Option<Vec<Landmark>>, r#box: Option<(f32,f32,f32,f32)>, frame_size: (usize,usize), score: f32, timings: StageTimings }` (defined in `src/core/mod.rs`); `frame_size` lets strategies normalise against the whole view. `timings.detector_us` / `timings.landmarker_us` are measured per frame and feed the dashboard's performance card.

3.  **Gesture Phase** (`src/gesture/`, implemented against `Strategy` in `src/core/mod.rs`): `main.rs` picks a strategy with `--gesture position|theremin`.
    *   `src/gesture/estimator.rs`: `HandEstimator::update(&HandDetectionResult) -> HandState { present, landmarks, hand_box, frame_size, confidence, tip, volume, geometry, jitter_px }`. This is the single source of truth about the hand: it owns the confirm/grace gate, the fingertip EMA, the geometry and the jitter measurement. Strategies read it and mutate nothing. `Pipeline::debounce` no longer exists - the gate lives here.
    *   `src/gesture/mod.rs`: the shared helpers - `band_position()` (the `NOTE_MARGIN`-inset playable band) and `spread_volume()` (thumb-index distance -> 0..1 loudness, normalised by the hand box, which is deliberately a different denominator from `geometry::spread`). `TipSmoother` is gone; the smoothing constant is in the estimator only.
    *   `src/gesture/keyboard.rs` — the default. The index fingertip's **position** on a **degree x octave grid** selects the note: columns are the scale's degrees (left = low), rows are octaves (top = high). `GridLayout::new(root, scale, octaves)` (`src/core/grid.rs`) picks the octave placement that best centres the grid inside `NOTE_LOW..=NOTE_HIGH` (C2–C6) and stores the notes row-major, top row first. The playable band is inset by `NOTE_MARGIN = 0.10` on both axes, and the canvas draws cells with exactly the same inset, so the lit cell is the one the hand is over. With the default 5-degree x 3-octave pentatonic grid a cell is ~102 x ~86 px on a 640x480 frame, so jitter cannot cross a boundary. Thumb<->index distance -> velocity/volume 0-1 (fingers apart is loud, a pinch is silent, saturating at `MAX_SPREAD = 0.6` of the hand box height). Unit tests cover both mappings, grid centring, corner clamping and the scale quantisation.
    *   `src/gesture/theremin.rs` — the continuous mapping: the tip's x sweeps `DEFAULT_LOW_HZ`..`DEFAULT_HIGH_HZ` (C2..C6, the same span the keyboard is allowed to reach) **logarithmically**, so half way across the frame is one octave up rather than half way in hertz, and nothing is quantised to a scale. Emits `Performance::Signal { frequency, amplitude }`, which the synthesizer glides and the MIDI sink ignores. `--theremin-low-hz` / `--theremin-high-hz` set the band.
4.  **Orchestration** (`src/pipeline.rs`): four stages on four threads.
    *   **Capture** (`capture_frames`) reads the webcam on its own thread into a **capacity-1 channel**; if inference is still busy, that frame is dropped and counted (`FrameMetrics::dropped`) instead of letting the pipeline drift behind the camera. `Pipeline::run` takes the `WebcamSource` out of the struct for this.
    *   **Inference** is the pipeline thread: `run` loops until an `AtomicBool` shutdown flag is cleared (set by `main` when the iced window closes, and by `run` itself on exit) or `--max-frames` is hit, calls `next_frame()` and then `advance()` on the result, and publishes a `FrameMetrics` clone into `Arc<Mutex<FrameMetrics>>`. There is no second single-threaded path - the tests call `advance(synthetic_frame(..))` directly.
    *   **Sinks** run on a third thread that owns the `Receiver<BusMessage>`, so a blocking MIDI write cannot stall a frame. `sinks` is an `Arc<Mutex<Vec<Box<dyn Sink>>>>`; the pipeline thread only touches it to push a waveform change from the pickers.
    *   **Presentation** runs on a fourth thread (`src/presentation/presenter.rs`) draining a capacity-1 `PresentJob` channel. The frame thread only *moves* the frame into that channel, and only when something is watching (`Presenter::wanted`). RGBA conversion, the ASCII render, the terminal print and `--ascii-dump` all happen there.
    *   **Control** lives in one place: `RuntimeConfig { active, feed, ascii, feed_fps, ascii_fps, ramp }` (`src/core/runtime.rs`), owned by the pipeline. The dashboard never writes it - it sends `UiCommand::{Start, Stop, SetFeed, SetAscii, SetRamp, SetInstrument}` down an unbounded crossbeam channel, and `advance()` drains the channel at the top of every frame. While `active` is cleared the capture thread sleeps and inference runs no frames, and `Pipeline::pause()` dispatches a release so the sinks go silent.
    *   `advance()` is five small stages - estimator `update`, `record_timing`, `update_tracking`, `dispatch_gesture`, `hand_over` - and then `publish` and `report_frame`. Debouncing goes through `HandEstimator` + `DetectionGate` (`src/core/detection_gate.rs`, 2 confirm frames / 3 grace frames): the anchor score flickers around the threshold, so a raw compare would click the note on and off. Inside the grace window the previous keypoints are kept instead of releasing.
    *   `Pipeline`'s state is grouped: `RunFlags { max_frames, emit_frames, debug }`, `Telemetry { started, last_publish, last_detection, avg_gap_ms, next_mock, the capture/inference/latency sample rings, the dispatch ring }`, `Presentation { jobs sender, presenter, stdout, dump }`, plus the stages themselves (camera, tracker, strategy, sinks, bus) and the estimator/gesture flags.
    *   `src/core/event_bus.rs`: `EventBus::new()` returns `(EventBus, Receiver<BusMessage>)`; `dispatch()` sends `BusMessage::Event(QueuedEvent { performance, dispatched_at })`, and `close()` sends `BusMessage::Shutdown` so the sink thread can block on `recv()` instead of polling.
    *   Stage timing lives in `FrameMetrics`: `frame_ms` is inference time, `capture_ms` the camera read, `latency_ms` the capture-to-publish gap, and `fps` is derived from the interval between published frames (not from the stage times, which overlap). Percentiles of each stage are kept in `src/core/telemetry.rs` (`Samples`/`StageProfile`) and printed by `--debug`.
    *   `src/core/types.rs` (21 lines): `enum Performance { Note { note, velocity }, Signal { frequency, amplitude }, Release }`. That is the whole vocabulary between the gesture layer and the outputs - no `text`, no `color`, no `note == 0` sentinel, no `event_type`.
    *   `src/core/geometry.rs`: `hand_geometry(&[Landmark])` derives resolution-independent descriptors (`spread`, per-finger `extension`, `tilt_deg`, `palm_length`) normalised by palm length. Strategies should reuse it instead of recomputing.

5.  **Output Phase** (implement `Sink`: `start`/`stop`/`handle(&Performance)`):
    *   `src/audio/synthesizer.rs`: `Synthesizer` — cpal output stream. The control side writes four atomics (`Target { sounding, frequency, amplitude, waveform }`); the callback owns a single monophonic `Voice` (target/current pitch, target/current amplitude, phase, timbre) with a 12 ms attack, a 60 ms release and a 15 ms pitch glide, and **takes no lock, allocates nothing and makes no syscall**. `cpal::Stream` is `!Send`, so it is wrapped in `StreamWrapper` with a documented `unsafe impl Send` - the one remaining `unsafe impl` in the project.
    *   `src/midi/mod.rs`: `MidiOutputEngine` — connects to a port whose name contains `--port` (default `OP-1`). `Performance::Note` goes through `NoteGate`, which enforces a `--min-note-ms` floor so a sweep across the keyboard is an arpeggio rather than 30 note-ons a second; `Release` sends exactly one note-off; `Signal` is dropped.
    *   `src/presentation/annotator.rs`: OpenCV skeleton overlay, used only by the offline `--image` dump.
6.  **Dashboard Phase** (`src/dashboard/`, iced 0.14, main thread):
      *   `dashboard/mod.rs`: `Dashboard` state (`boot`/`update`/`view`/`subscription`/`theme`). A `time::every(33 ms)` subscription produces `Message::Tick`, which takes the RGBA frame pixels out of the shared state (no copy) and clones the rest of the `FrameMetrics` into 120-sample ring buffers. Layout: window 1300x860; the skeleton stage on the left (the middle `row` is `.height(Length::Fill)` so the stage takes the whole middle band — a bare `row!` defaults to `Length::Shrink` and collapses it to the rail's intrinsic height) and a **scrollable 320 px rail** on the right with two tabs: **basic** = `INSTRUMENT` pickers, `OUTPUT`, `RENDER` (the ASCII charset pick list), Volume, Confidence, Status; **advanced** = Performance, Hand Geometry, the volume/confidence sparklines and the event log. The header carries a chunky `Start`/`Stop` button (`big_button`, green/red) that flips the pipeline's `active` flag, plus smaller `feed` / `ascii` / `box` / `labels` / `clear` toggles (`small_button`). The webcam image is only turned into an `image::Handle` when `show_feed` is on, and only when the pipeline's `--feed-fps` cadence (default 15) has produced new pixels — the previous handle is kept in between, so the preview runs slower than the skeleton rather than uploading a 1.2 MB texture every tick.
      *   `dashboard/skeleton.rs`: the stage canvas program. By default it draws no camera image: `backdrop()` fills the panel with a vertical gradient (`PANEL_TOP` → `PANEL_BOTTOM`), a soft centre glow ringed outward to the panel colour, and a thin `STAGE_EDGE` outline of the letterboxed frame region. When the `ascii` toggle is on, `ascii_art()` fills the **whole panel** (not just the letterbox) with the camera as block glyphs: `cell_grid()` derives the glyph size from `GLYPH_ASPECT = 0.6` (a monospace glyph is 0.6 em wide and 1 em tall) so the rows tile the panel without stretching, and one `fill_text` run is emitted per row - the geometry cost is `rows` text runs, not `rows * cols`. A row's alpha comes from `AsciiGrid::row_mean`, and rows below `ROW_SILENT` are skipped entirely; the tint is the colour of the note being played - `backdrop_colour()` blends `PITCH_COLORS` over the keyboard trail weighted by level squared, so a held key paints the art its pitch class and a note change cross-fades over `--fade-ms`, falling back to the nearest key implied by a theremin frequency and, with nothing sounding, to neutral `MUTED` grey. The art is drawn *before* `keyboard()`, so the grid and the skeleton sit on top of it, and if `feed` is on too the webcam image is painted over the art. `keyboard()` turns that region into the instrument by drawing the `GridLayout`: cells inset by `NOTE_MARGIN` on both axes (the same band the strategy reads), tinted by pitch class from `PITCH_COLORS`, with octave rows separated by a heavier line and labelled on the left, and note names printed in each cell when the cells are big enough. A cell's brightness comes from the UI's `note_trail` — the held cell glows and carries a volume bar rising from its floor, released cells fade out (top cap stays the most visible), with the decay time constant set by `--fade-ms` (`DEFAULT_FADE_MS = 450`, shown in the header as `trail 450 ms`). The 21-point skeleton is then drawn on top through the same `Mapping` (frame pixels → letterbox), with a translucent palm hull (`PALM_HULL`), a wide translucent under-stroke per bone for the glow, and haloed fingertip joints. `feed` puts the webcam frame back into the letterbox rectangle; the detector box and finger labels are optional.
    *   `dashboard/gauges.rs`: `Meter` (level bar) and `Sparkline` (rolling trace) canvas programs.
      *   `dashboard/metrics.rs`: `FrameMetrics` (the only UI-facing struct), `EventLogEntry`, `note_name()` (MIDI → scientific pitch name, 60 = C4), `note_index()` / `note_frequency()` / `fade_trail()` / `cell_index()` for the keyboard trail (`NOTE_LOW = 36`, `NOTE_HIGH = 84`).
    *   Never block the UI: the tick handler only clones the snapshot; drawing is pure geometry.

## Running It
Models live in `gesture_rust/assets/` and are **gitignored** — they must be present locally or the tracker fails at startup. The MediaPipe pair comes from the Unity/Sentis BlazeHand package (`mediapipe_hand_gesture-onnx-float.zip`; see `assets/new_readme.md`). Defaults:
`--detector-path assets/hand_detector.onnx`, `--landmarker-path assets/hand_landmarks_detector.onnx`, `--anchors-path assets/anchors.csv` (2016 anchors, normalised 0–1).

```bash
cargo run                                  # signal mode, audio output + dashboard
cargo run -- --mode midi --port OP-1       # MIDI output
cargo run -- --gesture theremin             # continuous pitch instead of the keyboard grid
cargo run -- --mode mock                   # synthetic animated hand: no webcam, no models
cargo run -- --no-ui                      # run the pipeline headless (no iced window)
cargo run -- --camera 1 --camera-width 1280 --camera-height 720   # different webcam / capture size
cargo run -- --debug                       # tracker diagnostics + a status line every 10 frames
cargo run -- --camera 1                   # pick a different webcam index
cargo run -- --model yolo --score-threshold 0.3   # single-pass Ultralytics pose model instead of BlazeHand
scripts/get_pose_model.sh fp16            # fetch a pose ONNX into assets/yolo_hand_pose.onnx (fp32 by default)
cargo run -- --ascii                       # ASCII art backdrop, on from the start

# ASCII art without a window - the quickest way to eyeball the renderer:
cargo run -- --mode mock --no-ui --ascii --ascii-cols 70 --max-frames 100
cargo run -- --ascii-dump art.txt          # write each rendered frame to a file

# Headless detection check without a webcam (best way to verify the box):
cargo run -- --image <any-photo-with-a-hand.png> --dump-frame output_frame.png --max-frames 1
```

## Development Guidelines for AI Assistants

### 1. Design Patterns
- **Trait-Based Abstraction**: To add a new output (e.g. OSC), implement `Sink` (`src/core/mod.rs`) and push it into the `sinks` vec in `main.rs`. New gesture logic means a new `Strategy` impl in `src/strategies/mod.rs`.
- **Coordinate discipline**: landmarks and boxes are always in **frame pixel space**, not normalised. Convert explicitly when feeding a model (192×192 detector, 224×224 landmarker) and convert back when drawing.
- **Error Handling**: Use `anyhow::Result` with `.context()`/`.with_context()` for model loading and frame I/O so failures name the file or stage.
- **Real-Time Constraints**: Keep `process_frame()` allocation-light; avoid blocking I/O (file writes, MIDI sends) inside the cpal audio callback — that callback must stay sample-rate safe.

### 2. Coding Style
- Follow standard Rust idioms (`rustfmt`/`clippy`), prefer explicit `?` over `.unwrap()`/`.expect()` in vision/audio paths.
- Treat the existing `unsafe impl Send for StreamWrapper` and `unsafe { ... }` pointer sampling as deliberate; add a comment explaining safety before touching them.

### 3. Never do these actions
- NEVER run `ls -R` — `target/` holds ~1.7 GB of dependency artifacts.
